# Project layout

`m31c -init` writes this layout; every app repo under github.com/qrazil follows
it. Directories are for finding files: the module name does not change when a
file moves, so a reorganisation costs only the `import` lines.

```
my-app/
  deps                     the project file; its directory is the project root
  deps.lock                generated by the first compile; commit it
  README.md                what it is, build, test, layout, release
  RENAMES.md               one entry per release: what moved or was renamed
  my_app.m31               entry point(s), at the root
  core/MA_core.m31         source, grouped in folders of your choosing
  tests/t_core.m31         one entry point per test, named t_*.m31
  tests/test.sh            the single way to run every check
  scripts/build.sh         build helpers; no tests live here
  docs/design.md           decisions, with the reasons
  .github/workflows/test.yml      linux x86-64, linux aarch64, macOS arm64
  .github/workflows/release.yml   on `v*` tags, after the same tests pass
```

A library (`m31c -init --lib`) has no entry point, no `scripts/build.sh`, and a
release workflow that only tests and publishes the source.

## Rules that make it work

- **The root is the nearest ancestor holding `deps`.** An entry file in
  `tests/` or `scripts/` finds the same project as one at the top.
- **Module names are globally unique and carry the project prefix**:
  `MA_core`, never `core`. Folders are never part of the name, so
  `import core.MA_core;` and `MA_core.greeting(..)` stay valid wherever the
  file sits. `m31c -lint` checks the prefix; entry points and files under
  `tests/`, `scripts/`, `docs/` and `corpus/` are exempt.
- **`tests/test.sh` is the one entry point.** It runs `m31c -fmt --check -r`,
  `m31c -lint`, then builds and runs every `tests/t_*.m31`; a test prints
  `N passed, M failed` last. CI calls it and nothing else, so a failure
  reproduces with one command: `M31_ROOT=<checkout or release> LANGC=<m31c>
  bash tests/test.sh`.
- **`deps`** lists `name <git-url> <sha>` or `name path <dir>`, after the
  `name` and `version` header lines. A dependency's first import segment is its
  name: `import tui.TUI_app;`.
- **A dependency's own `deps` is followed.** An app lists what it imports
  directly; a library lists what it uses, relative to its own directory. The
  top project's `deps.lock` and `.m31-deps/` pin and hold every git dependency
  of the whole graph, flat by name. One name must mean one source everywhere
  (a diamond is fine; a conflict or a cycle is an error naming the chain).
- **CI pins the toolchain** with `M31_REF` (a release tag of this repository)
  in both workflows. Moving it is a commit of its own.

## Versions

Before 1.0, a change that breaks how a consumer imports or builds the project,
including a regrouping of folders, is a **minor** bump, and `RENAMES.md` says
what moved. Bug fixes and additions are patch bumps. Pinning consumers
(`deps` lines) move on purpose, by sha.

## Starting one

```
m31c -init [--lib] [--name NAME] [--prefix PREFIX] [dir]
```

`NAME` defaults to the directory's name and must be lowercase words joined by
hyphens; `PREFIX` defaults to the name upcased (the initials of a hyphenated
name) and must be capital letters and digits. A name that is a standard library
module (`os`, `json`, ..) is refused. Nothing is overwritten: if any target
exists, nothing is written and the clashing files are listed. The generated
project passes its own `tests/test.sh` as it is.
